# 论文详解技术博客原则

本文是本仓库论文详解、科研笔记与相关技术长文的默认写作原则，来自用户在 SuperPoint 文章迭代中明确提出的偏好。后续 agent 开始写作或修改前必须阅读，并在用户没有另作要求时沿用。具体的新要求优先于本文；日常写作与可逆修改无需因为这些原则再次请求确认。

目标：让读者沿着**动机 → 初步思路 → 遇到的问题 → 改进机制 → 实验验证 → 剩余边界**理解论文，既看得懂直觉，也能追到关键数学与实现。不能只做机械翻译、论文摘要扩写，或把原文换成更口语的表达。

参考成品：[SuperPoint 文章](../src/content/blog/superpoint.md)。技术实现与踩坑处理见 [论文博客制作与排查指南](research-blog-production.md)；该文素材出处、提示词与生成参数见 [SuperPoint 素材记录](superpoint-assets.md)。

## 1. 从具体问题出发，让每个模块有来由

先说读者要完成什么任务，再说明为什么困难，最后引出术语与机制。用一个持续出现的场景贯穿全文，例如两张书桌照片、同一个书角、重复窗格；不要每讲一个模块就换掉全部例子。

引出一个模块时，应自然回答：

- 前一种做法已经解决了什么，为什么还不够？
- 新机制利用了什么额外信息或约束？
- 输入、中间结果和输出分别是什么？
- 它为什么有望改善问题，又增加了什么成本或假设？
- 论文拿什么证据验证，哪些情况仍然失败？

章节顺序服从这条问题链，不必复刻论文目录。例如可以先讲“真实图像标签从哪里来”，等读者理解监督来源后再介绍双分支架构。不要把所有动机挤在开头，后面突然切换成模块名和公式的罗列。

## 2. 硬核内容必须讲到能算、能画、能解释

直观不等于浅。决定方法成立的核心概念，应讲到读者能追踪一个具体输入、代入一个数值例子，并解释结果为何如此。

### 几何与数学概念

按需覆盖：对象及坐标系 → 数学定义 → 符号含义 → 具体例子 → 图像变化 → 适用条件 → 失效情形。

以单应矩阵为例，不能止于“一个矩阵描述透视变换”。需要让读者看见齐次除法、自由度、随位置变化的分母、前向点变换与逆向图像采样、插值和无效区域，以及二维变换和真实三维视角变化的区别。其他论文也应找出同等重要的基础概念，不能因为它“不属于本文贡献”就略过。

### 损失函数与优化目标

把总损失拆成有明确职责的部分，逐项说明：

- 监督从哪里来，标签怎样生成，约束哪个输出？
- 符号、维度、单位、取值范围是什么？
- 正负样本如何定义，和推理中的候选或匹配是否相同？
- 惩罚何时开启、何时为零，希望输出朝哪个方向变化？
- 权重在平衡什么，在哪些元素上求和或平均？
- 代入一个小例子会得到什么数值？全部输出相同等退化情况为什么不行？

优先配监督流向图、配对矩阵、概率条形图或直接按公式计算的损失曲线。不要只把公式放大、着色，随后用文字重复一遍符号名称。区分任务之间的权重与同一任务内部的权重；改变采样和平均方式后，不能暗示照抄系数就能复现原目标。

## 3. 原论文插图默认尽量完整覆盖

**先盘点原论文所有编号图，默认尽量都贴出来并讲解，而不是只选几张“够用”的网络图。** 方法、训练、数据、定性结果、定量曲线、消融和失败案例都属于精读范围；附录中有解释价值的图也应检查。

开始写作时，在素材文档中建立原图清单：图号、页码、内容、准备放入的章节。交付前逐项核对。确实省略重复内容、无关内容或无法可靠取得的图时，在素材文档中简记原因；不要无说明地只保留成功案例或原理图。

- 原图保留原论文图号，紧邻对应分析，不按博客出现顺序重编号。
- 每张图旁说明看哪里、比较什么、支持什么结论，以及不能推出什么。
- 原图中重要的坐标轴、图例、面板标签、误差条和数值必须保留。裁切不能改变实验含义。
- 原始图注不必整段贴进博客；保留图像内容，写自己的解读，并链接原文相应位置。
- 定量表格可以重排成可读表格，但数据、协议、阈值和出处必须保留。
- 不把所有补充图塞进末尾无解释的图库，不把“篇幅太长”当作默认省略实验图的理由。

SuperPoint 文章覆盖了 Figure 1–15，可作为覆盖方式的例子；15 张原图、30 张总图不是其他文章的固定指标。

## 4. 自制图补足直觉，不能只给架构配图

在写提纲时一起规划图。每个需要空间想象的关键机制、独立的失败原因与改进方向，都应考虑紧邻正文的解释图。用户指定的段落应逐一覆盖。不要在开头放一张总图，随后让最难的推导和局限部分恢复成连续大段文字。

| 内容 | 推荐画法 | SuperPoint 示例 |
| --- | --- | --- |
| 动机 | 同条件并列对比、局部裁剪 | 白墙、直边、角点及定位歧义 |
| 变换 | 同一输入的前后对照、坐标跟踪 | 同一桌面图的平移、旋转、仿射、透视 |
| 流程 | 实际中间对象与数据依赖 | 热力图、筛点、采样、匹配、几何验证 |
| 损失 | 标签构造、矩阵、精确函数曲线 | 65 类竞争、正负对应、间隔损失 |
| 局限 | 把信息缺失或歧义画出来 | 视差、重复纹理、没有候选点 |
| 改进 | 原方案与新增信息的对照 | 局部向量与上下文、整数与亚像素 |
| 实验 | 原图、协议一致的表格 | 聚合次数、噪声、匹配失败与成功 |

每张图要能用一句话概括它帮助读者理解的结论。图中应有正在讨论的图块、点、网格、向量、响应或曲线；不要把段落装进几个矩形，再用箭头串起来当作解释图。训练与推理、网络与后处理、检测与匹配、已知量与估计量应分清。

### 工具按表达目标选

- 几何、流程、向量、矩阵、图表等精确信息，优先程序生成的 SVG 或科学绘图。
- 需要自然纹理与场景时，可以使用真实素材或 ImageGen 生成写实源图。
- 图片变换对比使用同一张源图，由程序执行明确的变换并跟踪相同坐标；不要分别生成几张“看起来像变换过”的照片。
- 生成模型负责视觉素材，程序负责矩阵、坐标、插值、掩码、损失函数和数值。不要让图像模型凭感觉绘制精确公式、数据图或对应关系。
- 示意图与原论文图互补；自制图不能替代本应让读者看到的实验依据。

## 5. 科研风格靠信息表达，不靠装饰

使用干净底色、克制配色、统一线宽和足够留白；多面板用 `(a)`、`(b)` 等标记。文字在博客正文宽度下仍应可辨认，细节多的图提供原尺寸链接。

同图内颜色含义一致，并配合虚实线、形状或文字，避免只用颜色传达结论。标明必要的坐标、方向、单位、关键变量和图例。箭头必须表示真实依赖或坐标关系；交叉连线不能被误读为合并节点，也不要穿过标签。

不使用装饰性“科技感”、大面积渐变、图标堆砌掩盖内容。可以因文章主题调整风格，但同一文章的自制图应协调。已有图足够清楚时，不为增加数量重复画同一种机制。

## 6. 公式在正文与自制图中统一排版

默认采用论文式 Times 风格数学排版。本站现有实现是 **MathJax + STIX2**，在构建阶段生成自包含 SVG；STIX2 是 Times 风格数学字形，不应声称就是专有字体 Times New Roman。原论文图保留原始排版，不重新描摹作者标签。

- 行内变量和公式使用 `$…$`，独立公式用单独成行的 `$$` 包围，多行公式使用适当的 LaTeX 环境。
- 不用反引号、Unicode 上下标或临时 HTML `sup/sub` 拼公式。代码 API 名称才使用反引号。
- 向量、矩阵、上下标、转置、范数、希腊字母、算子使用规范 LaTeX，全文符号约定一致。
- 自制图内的公式共用 [数学渲染器](../scripts/lib/math.mjs)，避免正文像论文、图内却变成普通文本拼接。
- 公式附近解释符号与单位；代码编号和论文编号不一致时明确说明。
- 长公式在自身容器内横向滚动，不能把整页撑宽；手机上不要靠缩小到不可读解决溢出。

`<figure>`、`<figcaption>` 等原始 HTML 块里的 `$…$` 不能假定会经过 Markdown 数学解析。简单图注尽量使用自然语言；确需公式时应使用受支持的渲染路径并验证页面。图中文字的排版、转义和 SVG 嵌入注意事项见制作指南。

## 7. 实验讲清条件，也保留不利结果

先解释指标回答什么问题，再读数值。保留数据集、划分、分辨率、点数、阈值、匹配和后处理策略等影响可比性的条件。条件不同的两张表，不直接横向拼接排名。

- 区分检测重复性、定位误差、匹配精度、几何估计成功率等不同层面的指标。
- 区分教师或多次聚合的成绩、训练后学生的成绩、单次前向与整条系统链路的耗时。
- 配合消融解释“是哪一部分带来变化”，不把最终结果全归因于某一个模块。
- 主动讨论原图中的失败样本、严格阈值下的劣势和收益递减；避免只展示最好看的连线。
- 论文实验、作者代码、第三方复现、自己的公式推导与改进设想要分清。给后续方法一手来源，并指出它具体改善了哪层问题。

机制示意不是某后续方法的精确架构，人工曲线不是模型实测，概念类比不是作者已经验证的结论。提出可能原因时用相应的推测措辞，不能用一张结果表替代因果证据。

## 8. 引用简洁，详细记录留在仓库

正文保留必要的论文信息、图号、来源链接与参考资料，不堆砌版权声明、免责声明，也不要在每张图后反复写一段“非实测”声明。必要时用“教学示意”“按公式计算”“生成场景 + 确定性变换”等短语准确说明即可。

固定所用论文版本，引用尽量靠近对应内容。素材文档保存作者、版本、页码、裁剪参数、归属、生成提示词、源素材、计算假设与复现命令。网页保持流畅，仓库保留足够依据。

## 9. 长文必须便于翻阅

正文使用正常的 Markdown 标题层级，避免跳级；不要把标题写成加粗段落。长文应提供覆盖各级小标题的侧边目录，点击能准确定位，滚动时当前段落高亮，并让当前目录项保持可见。

手机端改为可折叠目录，跳转后收起；不能让长目录一直占满屏幕。图片可以点击放大，公式和表格各自处理溢出，正文不出现整页横向滚动。说明、公式和图片应紧邻，避免读者为一个定义上下翻多屏。

当前模板会为至少 5 个二级及以下标题的文章显示目录；目录实现见 [文章模板](../src/pages/blog/[...id].astro)。不要为每篇文章手写另一套目录。

## 10. 固定交付流程

1. **核对来源：** 阅读原文及必要附录，固定版本；建立原图清单，核对与论点有关的作者实现。
2. **规划叙事：** 列出问题推进顺序、核心概念、公式、原图与自制图的位置。每个机制有解释，每项实验有阅读目的。
3. **制作内容：** 写正文，提取原图，生成自制图；把脚本、必要源素材和素材记录一起保存。
4. **核对科学含义：** 检查符号、单位、对应关系、图中数字、权重与平均方式、实验协议、后续方法边界。
5. **逐图目视检查：** 原图核对裁切与图例，自制图实际渲染后检查文本、公式、箭头、坐标和重叠。SVG 语法正确不代表显示正确。
6. **核对页面结构：** 图片及大图链接、alt、真实尺寸、原图覆盖、自制图编号、公式渲染、标题锚点、目录层级与高亮。
7. **验证构建和阅读：** 内容或渲染改动运行 `npm run build`；涉及 Astro/TypeScript 模板或渲染配置时运行 `npm run check`。在桌面与约 390px 手机宽度检查关键段落及横向溢出。工具无法验证的部分如实说明。
8. **交付：** 简述新增内容、验证结果和本地／发布状态；不得把本地预览当作已上线。本次仅改文档时检查文档与链接即可，不必重跑无关构建。

文件组织和故障排查统一查阅 [制作指南](research-blog-production.md)。后续遇到可复用的问题时，更新这两份文档：写清现象、原因、做法与验证，不只追加一句“注意某某问题”。
